# Vitruvius software workspace

## Prepare the design library

`design_library_prepare` enables Design if needed and provisions the bundled library offline. It indexes the packaged presets, guides, design patterns and showcase recipes, installs the showcase reference cards and saves editable motion examples. The result reports available counts and what it added. Calls that leave data unchanged return no new undo token. A call that writes returns `design_library_undo` with a token for that preparation. Undo preserves pre-existing data and motion examples that have since been edited. The workbench button uses the same path. Remote source registrations keep their own separate ingest workflow.

## App project canvas

`app_project_preview` returns the current preview `url` and the stable `open_path` relative to the Design mount. Use `/design` plus `open_path` on the workbench host for a reusable browser link. Opening that link resolves an already running preview. Start and stop remain explicit tool operations.

Use `app_project_canvas_view` to read the project preview open in Applications and `app_project_canvas_act` to interact through its controls with a named cursor. With no open canvas, the tools report how to open it in Applications. The same bridge runs inside the project frame when Vitruvius is docked. For an annotated element, use `app_project_source_count` to check how many elements share its source and `app_project_edit_source` with the served revision to edit literal text, attributes or classes by position. The named cursor travels before the write and the open preview briefly outlines the result. The edit returns an undo call. The agent can declare an actor with its ID, name and color once per project. Subsequent canvas actions, source edits and edits through `app_project_canvas_edit` use that actor when the call identifies the same caller. Pass the selection target to identify the destination. Standalone exports run their saved source without preview markup or scripts. See [the canvas contract](docs/APP_CANVAS.md) and [the source editing workflow](docs/APP_PROJECTS.md).

The Canvas rail opens the regular copilot conversation scoped to the application project. It shows the person's request before the agent acts, the agent's visible speech, and collapsed groups of clicks, scrolling and navigation. Source history remains below the conversation, including affected files, example IDs and a token system ID when supplied. `app_project_update` accepts `examples` and `tokens_id` and also recognises the library metadata in `project.json`. Use `app_project_change_undo` with a history step ID and the current revision and timestamp. It reverses that step while preserving later edits to other files. A conflict on the same file keeps the later source, and success includes an undo call.

The Canvas panel also lists the active page’s elements and open comments. The person can jump to comment anchors, resolve comments and undo the latest source change from the history. `app_project_get` returns `history` with recorded source transitions, author (person or agent, plus agent name when supplied) and the last applicable source undo. Older saved revisions remain accessible with their existing IDs.

## App project data

Use `app_project_create` with `files` to create a custom project with a `vitruvius-app/v2` specification. `app_project_call` reads the schema and collection records, runs declared actions in SQLite and returns an undo call on success. Pass the same `request_key` when retrying the same confirmed action. See [the collection schema and routes](docs/APP_PROJECTS.md#collections-and-declared-actions).

`app_transfer_assistant_assets` supplies the panel and its streamed voice client. Save the complete asset set with `app_project_update` and keep its undo call. The owned preview relays full Spanish and English replies to the resident voice service while the panel keeps the written reply available. [Transfer assistant](docs/APP_TRANSFER_ASSISTANT.md)

## Form controls

Pass a page or fragment in `design_patterns(html=...)` to get `recommended_patterns`. `design_lint` and renders with lint also suggest `form-controls` when they see a form. `design_pattern(id="form-controls", lang="es-ES")` returns a working HTML page and a `recipe` with reusable `markup`, `css` and `script`. Link the project's token CSS and keep the form control names and accessible labels. The recipe uses native select and radio semantics, formats date entry from the document language (default es-ES), and submits canonical dates and 24-hour times. A calendar or clock button opens the system picker where available. Keep the native date or time input interface by placing `data-native-picker` on its wrapper.

The browser rule `form.native-unstyled` reports visible select, date, time, radio or checkbox controls whose computed appearance matches the native default at a measured width. It runs when the page exposes design tokens or `tokens_id` is supplied. The evidence includes affected widths. Styling the native controls preserves the system interaction.

## Web guides and craft library

For a new design, call `design_brief` with the full commission or `design_direction_brief` with its text. Use the resulting `content_sections` as editable drafts and open the real showcase recipes beside them. Before building, call `art_direction.create`, score all three library directions with `design_alternatives_evaluate` and record the choice with `design_alternatives_decide`. The typical direction is the baseline unless the commission explicitly requests it. Carry the result into a custom app using `art_direction_study_id`. Keep a simulation notice in the footer only when the commission asks for one. Existing requested notices stay in their own projects.

They are named in what an agent reads on connecting, read with `skills_list` and `skill_read`, searched and assigned with `skills_library` and `skills_assign`, and offered as prompts. The person chooses them on the skills page (`/api/agent/skills/page`) or in the hub's Skills tab; the `skills` block of `faustus-plugin.json` holds what the app asks for by default. The former apps that live on as modules answer to their old names through the same `compat_mcp` program (`compatibility/<id>/`), with their own skills: babel: `documentation-lookup`, `code-impact-analysis`, `learn-this-repo`; theseus: `reverse-engineering-workflow`, `code-impact-analysis`, `legacy-web-app-onboarding`.
