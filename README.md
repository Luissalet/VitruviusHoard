**Property tests and rule synthesis (Theseus).** `theseus_property_run` drives a target program (command or Python callable) with seeded composable input strategies and checks invariants, round trips, idempotence, metamorphic relations and reference-model comparisons written in the safe expression language, plus stateful command sequences (preconditions, model, postconditions) run against the real program; failures are shrunk by re-execution to a minimal case, and oracles that only compare the program with itself are warned about (docs/PROPERTIES.md). `theseus_synthesize` searches the same language for the simplest expression consistent with input/output examples and validates it against a reference program in a counterexample-guided loop, reporting coverage or the closest candidates, and can store the result as a rules-bank hypothesis (docs/SYNTHESIS.md). Evidence on executed runs only, never a proof or a completion claim.

**Rules bank and failure reproduction (Theseus).** Keep business rules extracted from a legacy program with statement, code evidence, examples and counterexamples; a rule stays a hypothesis until its executable check (a sandboxed safe predicate over case input and the reference program's output, with listed and generated cases) holds on every applicable case (`observed`) or yields a shrunk counterexample (`contradicted`), with status history and Markdown export (`theseus_rules_save`, `theseus_rules_read`, `theseus_rules_check`, `theseus_rules_export`). Reported failures are reproduced in fresh sandboxes, confirmed, minimised by delta debugging while the same failure signature is kept at every step, and written as a repro bundle with Windows and POSIX run scripts and an environment fingerprint; the bundle can be verified against another program such as a fixed version (`theseus_repro_create`, `theseus_repro_verify`). Observed rules and minimal inputs cover only the executed cases. See [docs/RULES-BANK.md](docs/RULES-BANK.md) and [docs/REPRO.md](docs/REPRO.md).

**Stateful sequences against a real HTTP service (Theseus).** `theseus_stateful_recipe_save`/`_read`, `theseus_stateful_run`, `theseus_stateful_replay` and `theseus_stateful_export` (HTTP `/api/projects/{id}/stateful/...`, MCP and the Theseus *Secuencias* tab) execute seeded action sequences against a test service started fresh on a free port per run (or a base URL with a reset request). ### Design rules, tiers and themes

Every lint check is a row of data in a registry (`design_rules_list`, `python -m vitruvius_hoard --list-rules`, `GET /design/api/rules`): a stable id, an engine (`static` reads the source and its cascade, `browser` reads the DOM snapshot of a real capture at each width, `visual` is judged by the vision model), a scope, a severity, a description, a reference and a pack (`core`, `slop/`, `quality/`, `craft/`, `unslop/`, `ds/`). 168 rules are registered; 155 are run by code and 13 are judged by the vision model. The craft and slop packs are original implementations guided by two openly licensed rule sets, and the `unslop/` pack (24 rules, mostly measured on computed styles) follows the sign list of unslop by Damir Sokolovsky (CC BY 4.0) (see THIRD_PARTY_NOTICES.md).

`design_lint`, `POST /api/lint` and `services.lint_html` accept `engines` (`static`, `browser`, `visual`). `engines: ["static"]` with `html` (or `path`) reads the source and its cascade alone and starts no browser, so it can run after every edit; without the parameter nothing changes.

`design_critique` groups findings in three tiers: Floor (severity error, never waived), Reflex (warning, waivable with a reason of at least 24 characters that restates neither the rule nor another waiver, and only for a rule that fired) and Finish (advice that never blocks). The gate passes only with no Floor finding and no open Reflex finding. `clean_review` makes one fresh call to the global model with only the screenshots, the HTML and the findings; its first word is recapture, rebuild, fix or ship, with at most eight findings, and a recapture or rebuild forces the gate to fix. With `tokens_id`, the `ds/*` rules compare the page with a saved design system (fonts, colours, radii, type scale).

`tokens_generate` and `design_brief` can deal themes (`theme`, `deal`, `genre`, `seed`, `reroll`): the last three builds and every theme that shares their paper/display/accent triple are blocked, and the same seed reproduces the same hand (`theme_deal`, `theme_check`, `theme_memory`, `theme_list`). `page_assay`/`page_check` accept `before` (save the links, fields, handlers and titles of a page, listed by `page_kept`) and `kept` (fail the check when any of them is missing after a redesign). The Critique screen exposes all of this: rule browser, tiers and gate, waiver form, clean-context verdict, design-system selector, theme dealer with its memory and the kept-elements comparison.

### Slop audit and direction brief

`design_slop_audit` (`POST /api/slop-audit`, button "Slop audit" on the Critique screen) renders a page at eight widths (320, 375, 414, 768, 1024, 1280, 1440, 1920), runs the core, slop, unslop, craft and quality rules and scores the slop from 0 (clean) to 100: each distinct sign adds its weight once. The `unslop/` rules read the computed styles of the real capture: gradient-filled text, coloured shadows and glows, purple gradient heroes, neon borders, too many grey text tints, headings at 800-900, more than eight font sizes, tracked uppercase labels, negative tracking on small text, one default sans for everything, emoji as interface icons, spacing off the 4px grid, identical cards in a row, uneven padding across sibling cards, greeting headlines, exclamation marks, full stops on labels, unsourced social proof, promotional badges, pills on every element, three or more buttons in the first screen and the centred hero stack; two more read the source (scale on hover, floating loops and parallax). The mode follows the score: `heavy` gives the full fix passes in order (spacing, color, icons, copy, type, layout, details, visuals, motion), `light` a short polish list and `none` says the page should be left alone. Each finding names its pass, tier and the widths where it fired; the screen marks it on the screenshot (click a finding to jump to its width and box). `design_direction_brief` (`POST /api/direction-brief`, button "5-line direction") has the family model write Product / Character / Bright moment / Signature / Avoid from the page's own text, with the slop signs of the audit in Avoid; without a model it falls back to the theme catalogue. Audits are kept under `data/slop-audits/` (`GET /api/slop-audit/<render_id>`). The audit, the brief and the rules list come in Spanish (Spain) or English: `lang` (`es` default, `en`) on `design_slop_audit`, `design_direction_brief`, `design_rules_list` and on the REST routes (or the Accept-Language header); the Critique screen passes its UI language, and `GET /api/slop-audit/<render_id>?lang=` re-reads a stored audit in the other language without auditing again. Rules, titles, fixes, pass names, summaries and the unslop credit have a Spanish table keyed by rule id (`vitruvius_hoard/i18n_es.py`); the brief is written by the model in the requested language.

### Presets and the registry

`design_preset_list` (`GET /api/presets`) holds 112 presets with full tokens: 25 authored ones (`vitruvius_hoard/presets.json`), one per hallmark theme (50, MIT) and the Hoard family palettes read from the shared `hoard-theme.css` (37). Each has light and dark colour roles with the shadcn/ui names (background, foreground, card, primary, muted, accent, border, ring...), radius, fonts, spacing, motion and a character line, plus the measured contrast of text and of the primary button. `design_pick_themes` (`POST /api/presets/pick`) proposes three for a brief with one recommended: keyword ranking over the catalogue, re-ranked with reasons by the family model when it answers. `design_preset_apply` (`POST /api/presets/apply`) writes a whole preset into a new design system, or only its colours, radius, type, spacing or motion into an existing one, and rebuilds the CSS and Tailwind exports. The Design systems screen has the preset picker with live light/dark swatches, the three picks and the partial apply.

### Import from Figma

`design_figma_import` (`POST /api/figma/import`, "Import from Figma" on the Design systems screen) reads a frame through the Figma REST API with a personal access token saved in Settings (kept in `data/figma-token`, never in the repository), or from the JSON of `GET /v1/files/:key/nodes` pasted in. The frame is reduced to a compact spec (auto-layout read as flex, sizing as fixed / hug / fill, repeated fills, strokes, effects, radii and text styles collapsed into named style ids), rendered to HTML/CSS, captured, turned into a design system (colour, fonts and radii of the frame), critiqued against that system and compared pixel by pixel with Figma's own PNG of the frame. The comparison covers the canvas of both images: a render of another width is scaled to the frame width and reported as `normalized` with its `render_scale`, and so is a frame shorter than the 900px capture viewport, whose flat padding rows below the frame height are dropped and counted in `viewport_fill_rows` (anything drawn there still counts); rows that only one image has (a truncated render, an extra footer) count as different and the result is labelled `partial` with both sizes, the compared rectangle, `coverage`, `missing_rows`/`extra_rows` and the difference inside the shared area (magenta in `diff.png`). It is a pixel measure, not semantic equivalence. Files are under `data/figma/<id>/` (`spec.json`, `page.html`, `figma.png`, `diff.png`). Without a token the dialog says what to paste and where, and takes the frame's PNG exported from Figma as a file so the pixel difference also works with pasted JSON.

### Sound in motion

A motion composition can carry sound as data: `sound` holds `{t, rol}` events (`t` in seconds, `rol` one of 21 roles such as `hit`, `pop`, `click`, `text`, `whoosh.short`, `whoosh.long`, `rise`, `success`, `error`) plus a style (`calm`, `crisp`, `minimal` or `launch`). `motion_sound_plan` (read-only) proposes events from the scene changes, texts and shapes without rendering anything; `motion_sound_render` mixes the track and returns the WAV, the loudness and, for every event, the requested time, the time measured in the rendered audio and the error in milliseconds; `motion_render` with `audio: true` muxes the same mix into the MP4 (AAC 192 kbit/s, 48 kHz, stereo, length equal to the video). Sounds come from the effect bank and kit of an MIT-licensed open library (earshot, see NOTICE); no sound model is loaded, only its procedural bank is used. Each sound is placed by its measured onset or peak, not by the start of the file, so the hit lands on the frame where the change happens (measured error under 3 ms in the live check; a whoosh is placed by its peak, which comes after its rise).

The mix is brought to -14 LUFS with a true peak of at most -1 dBTP through soft saturation plus a look-ahead limiter. Effects with a very high crest factor can make -14 LUFS unreachable without audible distortion; then the result says `reached: false` and reports the loudness it did reach, never a made-up figure. The per-event measurement inside the finished track is only reported for events that do not overlap another sound. The HTML export stays silent. The library is an optional extra (`pip install "vitruvius-hoard[sound]"`, which installs numpy, scipy, soundfile, soxr and pyloudnorm, and the library itself from its repository with `--no-deps`); without it the tools answer with the install hint. The Motion screen has a Sound section: style, automatic sound for changes, an editor of effects by second, "Mezclar y escuchar" with a player and the measurement list, and the MP4 export carries the sound.

### SEO and GEO audit

`site_audit` audits a site with repeatable measurements and returns a score, categories with findings and a phased action plan (`docs/SITE-AUDIT.md` has the full contract). It reads the home page and the pages of the sitemap and its links (10 by default, 40 at most) and checks indexability (`noindex`, robots.txt, sitemap, canonicals, redirects, soft 404), security headers, broken links, on-page elements, JSON-LD, images and the AI crawlers in robots.txt, separating the ones that train models from the ones that search and cite (blocking training does not stop citing). Core Web Vitals (LCP, CLS, INP estimate, FCP, TTFB, TBT) are measured in a real Chromium load of a throttled mobile profile; they are lab data, not real users. Categories weigh content 23, technical 22, on-page 20, schema 10, Core Web Vitals 10, AI visibility 10 and images 5; a category that could not be measured has no score and stays out of the total. What a measurement cannot decide (editorial quality, E-E-A-T, search intent, a training opt-out) is marked `judgement: true`, is never scored and goes to a human-review phase. When the initial HTML is an empty shell filled by scripts, the page checks read the rendered DOM and `ai.js-dependent` warns that crawlers without scripts see nothing. `site_audit_reports` lists the saved reports or returns one whole; each report carries `previous` (new and fixed finding ids against the last audit of the same url), which a periodic monitor can use for drift. The Audit screen shows the score, the categories, the plan, the vitals, the crawler table and the saved reports.

## Alternatives and instruments

**Design by comparable alternatives** (`design_alternatives_*`, `/api/design-alternatives`, the **Alternatives** screen): a brief, criteria frozen before measuring (computed from critique, lint, contrast, page_check, DOM and performance numbers, or a manual score with a rationale), and 2 to 12 pages, app projects or diagrams that must differ in structure; colour-only variants are refused with the reason. Every alternative is measured with the existing tools, then Vitruvius computes the Pareto frontier, trade-off sentences with numbers, a ranking that can be re-weighted without measuring again, and records the decision with its reason. Changing criteria after measurement needs a new study revision. See `docs/ALTERNATIVES.md`.

**Instrument factory and explainer** (`instrument_*`, `/api/instruments`): a typed spec (inputs with units and ranges, formulas or operations, outputs, examples) becomes an app project with source kept, generated tests and a stdlib-only standalone export; `instrument_check` extracts the export, runs its tests and server, recomputes the spec's examples and checks that the worked-example explainer shows the same numbers as the instrument. See `docs/INSTRUMENTS.md`.

## Protocol checker

The **Protocols** screen, `/api/protocols/*` and the `protocol_check` tool explore every interleaving of a small bounded protocol (shared state, atomic labelled steps, nondeterministic choices, bounded crashes with restart) and check invariants, end conditions and deadlock. A violation comes with the shortest counterexample, a step-by-step replay and a pytest file to reproduce it on the real system; `holds` means the whole reachable space within the bounds was checked, under the listed assumptions. Schedules and exported hooks retain nondeterministic branch indices. Replay checks initial and terminal properties as well as intermediate states; dictionaries remain distinct from sequences in state hashing. Corrections 2007 are integrated after independent review (submission 1, source 001e6a0; merge 14eb782), with 38 passing protocol/catalog tests and native MCP/browser checks from Main. See `docs/PROTOCOLS.es.md`.
